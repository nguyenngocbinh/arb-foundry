Arb Foundry

A modular foundation for researching cross-exchange crypto arbitrage without placing real orders.

Safety boundary: live order submission is not implemented. Public spot market-data adapters and a configurable health-check runner are implemented. The depth-aware scanner produces research candidates only; it never submits orders.

Scanner assumptions

Fee rates are explicit decimal fractions of quote notional (0.001 = 0.1%) and are illustrative unless verified independently. The scanner assumes fees on quote notional for both legs, requires the full target base quantity to be visible on both sides, and rejects stale books. The separate paper simulator checks book freshness and cross-venue timestamp skew, optionally validates supplied symbol filters, applies assumed fees and adverse slippage, and can reject or model a paired partial fill. It never sends orders. Symbol filters are not auto-fetched and are not yet wired into the scanner. SQLite can persist simulation outcomes and pre-trade rejection events. PortfolioStateStore persists versioned portfolio snapshots in SQLite and verifies SHA-256 checksums on recovery. Use apply_trade_and_save for durable accounting; snapshots do not yet include complete order-book replay inputs and the checksum is not tamper-proof. Audit storage is not tamper-evident. The system does not model transfer/withdrawal costs, inventory availability, latency, rebates, funding, changing books, or execution probability. An opportunity is not a promise of profit.

Reproducible research

MarketReplayStore saves ordered bid/ask levels, source timestamps, fee assumptions, target quantity, scanner thresholds and the original scan clock. Replay reconstructs the same typed inputs and reruns the scanner using that saved clock; it does not query exchanges or submit orders. SHA-256 is corruption detection, not tamper-proof audit.

Persistent paper kill switch

A SQLite-backed switch defaults to HALTED and requires an explicit arm transition. When supplied to the simulator it checks state before fill calculations; missing/invalid state and database read failures do not permit the simulation. This is not a distributed or live-execution safety control. See kill-switch behavior and limitations.

Calculation documentation

Calculation methodology documents VWAP, gross/net PnL and spread in basis points, fee assumptions, symbol filters, freshness/skew gates, slippage, partial-fill behavior, SQLite audit events, worked numerical examples and modelling limits.

Implemented health checks

The health-check service checks public exchange endpoints at startup and repeats at a configurable interval (24 hours by default). It records health, check time, latency and an error summary in memory. The application host must start the runner in a managed worker; no service starts automatically at import time.

Implementation phases

  2. Public market-data adapters, freshness validation and health-check service.
  3. Depth-aware spot arbitrage scanner and net-spread calculation.
  4. Separate strategy modules for spot–spot and spot–perpetual research.
  5. Paper trading, risk limits, persistence and recovery tests.
  6. Evaluation reports, operational guidance and documentation.

Engineering rules

  • Paper trading only by default; no secrets in Git.
  • Reject stale data and insufficient order-book depth.
  • Every milestone requires automated tests and traceable evidence.
  • Changes stay on feature branches; merging into main requires explicit approval.
